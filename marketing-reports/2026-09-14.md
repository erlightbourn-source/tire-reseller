## SHARPENED RECOMMENDATIONS (new this pass — a concrete fix path for each, not a repeat flag)

### T3-fix. Anchor "verified" to `User.emailVerified`, not billing status
**Stage:** Trust
**What & why:** The schema already has a real, meaningful verification signal —
`User.emailVerified` (`prisma/schema.prisma:43`) — that today's seller-profile page doesn't
even select (confirmed while scoping today's safety-audit `select` fix on that route). Two
low-effort options, either closes the copy/reality gap without touching monetization: (1)
rename the badge/copy from "verified seller" to "founding seller" / "seller plan" (accurate,
already true) and drop "verified" entirely from `app/page.js`/`lib/content.js`/
`app/founding-seller/page.js`; or (2) if "verified" is worth keeping as a trust word, gate it
on `seller.emailVerified` (every real account already has this at signup) rather than on
`pro`/`foundingSeller` — a $10/mo payment and an email click are very different trust signals,
and conflating them is the actual gap, not the word itself.
**Where:** `lib/content.js:52`, `app/founding-seller/page.js:25`, `app/page.js:29,111,143`;
`lib/seller.js` (`isProSeller`) if option 2.
**Effort:** S (copy-only for option 1; option 2 needs `emailVerified` added to the seller-page
`select` + one new helper). **Confidence:** high — this is a factual-accuracy fix, not a taste
call.

### T4-fix. Compute a real reply-time signal from `Message` timestamps, or drop the line
**Stage:** Trust → Conversion
**What & why:** This week's messaging-notification build (`lib/notify.js`, merged 2026-09-13)
already proves the data model supports exactly this: it computes "is the recipient caught up"
from `Message.readAt`/`createdAt` per thread. The same query shape — median time between a
buyer's first message and the seller's first reply, over the seller's last N threads — would
turn "Usually responds within a day" from a static lie for every Pro seller into a real,
trust-building number ("Typically replies in ~3 hours," or nothing at all for a seller with no
reply history yet, which is more honest than a blanket claim). If that's more than this week's
effort budget, the safer interim move is deleting the line — an unearned trust claim is worse
than no claim once a buyer catches it wrong.
**Where:** `app/listings/[id]/page.js:237`; new query alongside the existing thread/message
routes (`app/api/messages/[threadId]/route.js` already has the exact `readAt`/`createdAt`
shape to model this on).
**Effort:** M (real version — a new aggregate query + caching thought, since running it
live on every listing-detail render is wasteful) / S (interim — delete the line).
**Confidence:** medium-high on the value; the effort estimate for the real version depends on
whether it's computed live or backfilled/cached, which is a data-engineer implementation call.

## ONE NEW OBSERVATION — the 2026-09-13 consent gate is a clean example of doing friction right
**Stage:** Activation (no action needed — a positive note for the pattern library)
**What:** The new signup Terms checkbox (`components/AuthForm.js:204-219`) is unchecked by
default, opens Terms/Privacy in a new tab (doesn't lose the signup form), disables the submit
button until checked (no dead-click-then-error-toast), and states the marketplace/no-party/
own-risk framing in plain language rather than legalese. This is required friction added
without becoming a dark pattern or an unnecessary funnel leak — worth using as the reference
shape next time a required-consent UI is needed elsewhere in the app (e.g. if a future returns/
guarantee mechanism needs its own assent step).
