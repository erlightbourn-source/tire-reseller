## (c) Proposed for review
- **`31127aa` — PROPOSAL: make `/api/email-alerts` enumeration-safe.** The route returned `{ok:true, duplicate:true}` for an already-registered `(email, query)` pair vs `{ok:true}` for a new one, letting a probe (behind the 5/min IP + 3/hr per-address caps) distinguish alert members from non-members — an enumeration-symmetry gap on a user-data route (security floor). Changed both branches to a uniform `{ok:true}`, matching the confirm route's enumeration-safe redirect. The client never reads `duplicate` (`EmailAlertForm` uses only `data.error`), so real users see no change. Build + 64 tests green; schema restored to postgresql.
  - **Decision Evan owns:** confirm you want full enumeration symmetry here (privacy-preserving, standard for opt-in endpoints). The only tradeoff is that a re-signup no longer carries a distinct "already on the list" acknowledgement — which the UI never surfaced to the user anyway.
