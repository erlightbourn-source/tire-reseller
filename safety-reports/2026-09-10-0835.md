## (b) Improved (shipped directly, non-auth-flow, low-risk)

- **`264c27e` — BACKLOG #24: explicit `select` on `app/sellers/[id]/page.js`'s Prisma
  query.** Previously used `include` (whole-row fetch), pulling `passwordHash`/
  `resetTokenHash`/`email`/`stripeCustomerId`/`tokenVersion` into the server-render
  payload on an anonymously-viewable page. Verified this was **not a live leak**
  today — RSC only serializes fields the JSX actually reads, and I confirmed the
  new e2e assertion passes against the pre-fix code too — but the query shape put
  those columns one future JSX change away from rendering. Fix closes the class of
  bug at the query, not the current symptom: those columns are no longer fetched
  for this page at all. New e2e regression test added
  (`e2e/flows.mjs`: "seller profile page never leaks passwordHash into the
  rendered page").
- **`48bbf55` — BACKLOG #26: allowlist fields sent to `ERROR_WEBHOOK_URL`.**
  `app/api/client-error/route.js` is intentionally unauthenticated (anon users hit
  client errors too) but spread the raw request body wholesale into the outbound
  webhook payload — any caller could inject Slack `blocks`/`channel`/`attachments`
  or poison a Logtail/Sentry-tunnel schema. Extracted `lib/errorWebhook.js`'s
  `buildWebhookPayload`, which picks `text`/`url`/`digest` explicitly. 3 new unit
  tests prove an injected override never reaches the payload and that url/digest
  still truncate at 500/200 chars.

Both verified: build clean (`APP_SECRET=... npm run build`), 86/86 unit tests
(`npm test`), 12/12 e2e (`npm run test:e2e`), schema provider restored to
`postgresql` after each build.
