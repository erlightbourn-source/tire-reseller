### Investigation that did NOT ship (and why — this is the substance of today's pass)
Set out to close BACKLOG #5 (loading.js gaps) by adding `loading.js` to the 5 routes
with genuine DB fetches and no loading boundary: `listings/[id]`, `messages`,
`messages/[threadId]`, `sellers/[id]`, `tires/[brand]`. (Correction to the 8/17 report:
its named gap list — `sell`, `sell-tires`, `pro`, `subscribe`, `sell/bulk` — turned out
on inspection to have no real `await prisma...` calls; near-instant pages, low value
for a loading.js. The routes above are the actual gaps with real fetches.)

Drafted all 5, built clean, 66/66 tests passed — then verified by observation with a
live `next start -p <port>` + `curl -D -` smoke test (not just build/test) per the
Cowork Bible's verify-by-observation rule, and it caught a real regression:

- `curl http://.../listings/nonexistent-id` → **HTTP 200** with "Page not found" in the
  body, instead of a real 404. Confirmed by A/B: removing the new `loading.js` restored
  `HTTP 404`.
- `curl http://.../messages/nonexistent-thread` (unauthenticated) → **HTTP 200** full
  page HTML instead of `redirect()`'s real `307`. Confirmed by A/B: removing
  `app/messages/loading.js` (a **parent** segment, inherited by the child route)
  restored `HTTP 307`.

Root cause: a `loading.js` opens a streaming Suspense boundary, which commits the HTTP
status as 200 before the async page component runs far enough to throw
`NEXT_NOT_FOUND`/`NEXT_REDIRECT`. This reproduces from BOTH (1) a `loading.js`
colocated in the *same* segment as the `notFound()`-calling page, and (2) a *parent*
segment's `loading.js` inherited by a `notFound()`/`redirect()`-calling child route —
broader than the existing code comment described (it only named the ancestor-layout
case). All 5 of today's drafted `loading.js` files were **reverted, none committed**;
working tree confirmed clean before proceeding. Corrected the comment so this doesn't
cost another investigation next time. BACKLOG #5 moved to `needs-plan` — the real
fix is a client-side loading affordance (e.g. `useLinkStatus` / nav-progress bar) that
doesn't touch the server response, not a route-segment `loading.js`.

BACKLOG #7 (query efficiency) spot-checked: no new N+1s in `app/page.js` /
`app/browse/page.js`; the one `take: 2000` (radius-search bounding-box prefilter) is a
deliberate, already-commented cap, not a gap — left pending, needs real load data to
prioritize further rather than a guess.
