## (c) Proposed for review — committed, needs Evan's PR review

**`bb27e53` (PROPOSAL, backlog #3) — Hash the email-alert CONFIRM token at rest.**
Closes the plaintext-confirm-token half of the carried "email-alerts token at rest" finding (2026-07-02 flag #2). The confirm token is a one-time secret (emailed once, nulled on use), so it now follows the same hash-at-rest pattern as reset/verify tokens (`lib/auth.js`): `app/api/email-alerts/route.js` stores `confirm.hash` and emails the plaintext; `app/api/email-alerts/confirm/route.js` hashes the incoming token before matching. A leaked `emailAlert` row can no longer be replayed to confirm alerts.

- **Scoped deliberately:** the **unsubscribe `token` stays plaintext by design.** It is a *persistent* capability the alerts cron re-emits in the unsubscribe URL + `List-Unsubscribe` header on every digest (`app/api/cron/alerts/route.js:88,95`), so the server must regenerate the link from stored data — hash-at-rest would break every digest's unsubscribe link. It is 256-bit unguessable and grants only unsubscribe (low harm). The real fix is a per-email HMAC redesign → backlog #3a. Both routes document this.
- **Decision point for Evan:** severity is low, so this is a PROPOSAL (auth/token flow), not an auto-fix. Merge to adopt hash-at-rest for confirm tokens.
- **Backward-compat note (from the reviewer):** any `emailAlert` row created *before* this change has a plaintext `confirmToken`; an old confirm link would now hash → no match → the confirm becomes a **silent no-op** (redirects to `/alerts-confirmed` but doesn't set `confirmed`). No crash, no data loss (`updateMany` on 0 rows). Acceptable pre-launch (≈0 outstanding rows); a one-line ack, not a blocker.
- **Verification:** `APP_SECRET=… npm run build` OK; `npm test` **61/61**; confirm-token contract observed directly (stored ≠ plaintext; `hashResetToken(plaintext)` == stored → new match works; old plaintext-match would fail → the change is load-bearing; 64-hex sha256). Schema provider restored to `postgresql`.
